# Mini NPU 시뮬레이터

MAC(Multiply-Accumulate) 연산으로 3×3부터 25×25까지의 패턴(Cross / X)을 판별하는 Python 콘솔 프로그램입니다.

## 실행 방법

- 환경: Python 3.8 이상, 외부 라이브러리 없음 (json, time만 사용)
- `main.py`와 `data.json`을 같은 폴더에 둡니다.

```bash
python main.py
```

- 실행 후 모드를 선택합니다.
  - `1`: 사용자 입력 (3×3 필터 A, B와 패턴을 한 줄씩 공백으로 구분해 입력)
  - `2`: data.json 분석 (5×5, 13×13, 25×25 패턴을 일괄 판정)

## 구현 요약

- **MAC 연산**: 이중 반복문으로 같은 위치끼리 곱하고 모두 더합니다. `n = len(pattern)`으로 크기를 자동 판별해 모든 크기를 처리합니다.
- **점수의 의미**: 점수가 높을수록 입력 패턴이 해당 필터와 더 유사합니다. 예를 들어 십자가 패턴 `0 1 0 / 1 1 1 / 0 1 0`을 같은 모양의 필터와 곱해 더하면 5점, X 필터와 계산하면 1점입니다.
- **N의 정의**: 이 문서에서 N은 패턴의 한 변 길이이고, 연산 횟수는 N×N = N²입니다.
- **라벨 정규화**: `normalize_label()`이 앞뒤 공백 제거와 소문자 변환 후, `+`/`cross`는 `Cross`, `x`는 `X`로 통일합니다. 필터 키와 expected 값 모두 이 함수를 거치고, 출력과 PASS/FAIL 비교는 표준 라벨 기준입니다.
- **동점 처리(epsilon)**: `abs(a - b) < 1e-9`이면 동점으로 보고 `UNDECIDED`로 판정합니다. 상수 `EPSILON`으로 한 곳에서 관리합니다.
- **EPSILON(1e-9) 선택 이유**: 부동소수점 누적 오차는 약 1e-16 수준이고 데이터의 실제 점수 차이는 0.1 단위 이상이므로, 오차보다 충분히 크고 실제 차이보다 훨씬 작은 1e-9를 기준으로 삼았습니다.
- **입력 검증**: 모드 1은 줄당 숫자 개수와 숫자 파싱을 검사하고, 오류 시 안내 문구 출력 후 해당 행렬을 처음부터 다시 입력받습니다.
- **스키마/크기 검증**: 모드 2는 키(`size_N_idx`)에서 N을 추출하고, 필터 존재 여부, Cross/X 라벨 존재 여부, 패턴 크기 일치를 확인합니다. 문제가 있으면 프로그램을 멈추지 않고 해당 케이스만 FAIL로 기록합니다.
- **성능 측정**: `time.perf_counter()`로 `mac()` 호출 구간만 10회 측정해 평균(ms)을 냅니다. 입출력 시간은 제외했습니다.
- **알 수 없는 라벨**: `normalize_label()`이 `None`을 반환하면 해당 라벨은 무시되고, 필터가 부족하면 그 케이스는 FAIL로 기록됩니다.
- **허용 키 형식**: 패턴 키는 `size_{N}_{idx}` 형태여야 하며, 두 번째 조각에서 N을 추출합니다.
- **모드별 동점 표기**: 모드 1은 A/B 비교라서 "판정 불가", 모드 2는 표준 라벨 비교라서 `UNDECIDED`로 표기합니다. 의미는 같습니다.

## 새 라벨 추가 절차

현재 표준 라벨은 `Cross`, `X` 두 개입니다. 새 라벨(예: `Circle`)을 추가하려면 아래 순서로 진행합니다.

1. **정규화 규칙 추가**: `main.py`의 `normalize_label()`에 새 표기를 추가합니다. (예: `if text in ("o", "circle"): return "Circle"`)
2. **data.json 필터 추가**: `filters`의 각 `size_N`에 새 라벨 필터를 넣습니다. 필터 키는 정규화 규칙에 해당하는 이름(예: `"circle"`)을 사용합니다.
3. **판정 로직 확장**: `judge()`와 모드 2의 점수 계산 부분이 두 필터(Cross, X)만 비교하므로, 새 라벨의 점수도 계산해 가장 높은 점수의 라벨을 고르도록 수정합니다. 동점은 기존처럼 epsilon으로 판단합니다.
4. **출력 확인**: 케이스별 점수 출력에 새 라벨 점수 줄을 추가하고, PASS/FAIL 비교가 표준 라벨 기준으로 동작하는지 확인합니다.
5. **테스트 케이스 작성**: `patterns`에 새 라벨 패턴과 `expected` 값을 추가하고, 정규화된 라벨과 expected가 일치하는지 실행해 검증합니다.

## 결과 리포트

### 실행 결과 요약

총 테스트 6개, 통과 3개, 실패 3개입니다.

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

### 실패 원인 분석

1. 실패 3건(size_5_1, size_13_2, size_25_1)은 모두 두 필터의 점수가 사실상 같아 UNDECIDED가 나온 경우입니다.
2. 원인을 분류하면 데이터/스키마 문제도, MAC 로직 문제도 아니고 **수치 비교(동점) 문제**입니다.
3. 라벨(`+`, `x`)은 정규화로 정상 처리되었고, 필터 키와 크기 검증도 모두 통과했습니다. 나머지 3건은 정상 판정되어 MAC 로직도 올바릅니다.
4. 실제로 점수를 손으로 계산하면 세 케이스는 수학적으로 정확히 같은 값입니다. size_5_1은 Cross가 중앙 1칸만 겹쳐 0.9, X는 대각선 9칸 × 0.1 = 0.9입니다.
5. size_13_2는 Cross가 25칸 × 0.3 = 7.5, X는 중앙 1칸만 겹쳐 7.5입니다. size_25_1은 Cross가 4.9, X가 49칸 × 0.1 = 4.9입니다.
6. 컴퓨터는 0.1이나 0.3 같은 소수를 2진수로 정확히 표현하지 못해 누적 합에 약 1e-16 수준의 오차가 생기고, 그래서 `0.8999999999999999` 같은 값이 나옵니다.
7. `==`로 비교했다면 이 미세한 오차 때문에 우연히 Cross 또는 X가 이기는 잘못된 판정이 나왔을 것입니다. epsilon(1e-9) 정책 덕분에 오차보다 크고 실제 차이보다 작은 기준으로 동점을 일관되게 처리합니다.
8. 정책상 동점은 UNDECIDED이고 expected와 다르므로 FAIL로 집계됩니다. 이는 의도된 동작이며, 기준을 바꿔 PASS로 만들지 않았습니다.
9. 라벨 정규화를 하지 않았다면 판정 `Cross`와 expected `+`가 달라 정상 케이스까지 FAIL이 되었을 것입니다. 정규화가 이를 막았습니다.

### 성능 분석 (10회 평균)

아래 값은 각 크기별 MAC 연산을 **10회 반복 측정한 평균**입니다. 별도의 워밍업 실행은 하지 않았습니다.

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.0016 | 9 |
| 5×5 | 0.0029 | 25 |
| 13×13 | 0.0143 | 169 |
| 25×25 | 0.0387 | 625 |

### 시간 복잡도 분석

1. MAC은 N×N 이중 반복문에서 곱셈과 덧셈을 N²번 수행하므로 시간 복잡도는 **O(N²)** 입니다.
2. 3×3에서 25×25로 가면 연산 횟수는 9 → 625로 약 69배 늘고, 측정 시간은 0.0016ms → 0.0387ms로 약 24배 늘었습니다.
3. 13×13에서 25×25로 가면 연산 횟수는 약 3.7배, 시간은 약 2.7배 늘어, 큰 크기에서는 연산 횟수 증가와 시간 증가가 비슷한 방향입니다.
4. 시간 증가 배수가 연산 횟수 배수보다 작은 이유는 작은 크기에서 함수 호출, 반복문 시작 같은 고정 비용이 차지하는 비중이 크기 때문입니다. 크기가 커질수록 N²항이 지배적이 됩니다.
5. 측정값은 실행할 때마다 조금씩 달라집니다. 연산이 매우 짧아 운영체제 스케줄링 같은 외부 요인의 영향을 받기 때문입니다.
6. 결론적으로 크기가 2배가 되면 연산량은 약 4배가 되며, 실제 AI 모델처럼 큰 필터를 수천 개 쓰면 연산량이 급증해 병렬 처리가 가능한 NPU가 필요해집니다.
7. N=1000이면 연산 횟수는 100만 번입니다. 순수 파이썬 반복문은 25×25(0.04ms)의 1,600배 규모이므로 단순 환산으로 수십 ms 수준이지만, 필터가 수천 개면 곧 초 단위가 됩니다. 이때 우선 최적화 대상은 반복문 오버헤드와 메모리 접근 패턴입니다(보너스 과제의 1차원 배열 변환).
8. CPU는 직렬 처리와 명령 해석 오버헤드가 병목이고, NPU는 많은 MAC을 동시에 처리하되 메모리 대역폭(데이터를 연산 장치로 공급하는 속도)이 병목이 되기 쉽습니다.
